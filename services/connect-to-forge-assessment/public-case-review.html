The starting point

samid737/jira-checklist-plugin is a small publicly readable Jira checklist plugin using atlassian-connect-express. Its Connect descriptor defines a web panel at atl.jira.view.issue.left.context, JWT auth and installation lifecycle. Its documented feature is an editable checklist attached to Jira issues.

Six specific decisions before a Forge rewrite

01 · UI module mapping

Does the panel still appear when users expect it?

The Connect panel location maps to Forge jira:issuePanel according to Atlassian's equivalence table. The Forge panel has different show-button and visibility semantics, so module name parity alone is not user-experience parity. Test with an issue viewer and editor.

02 · Data continuity

Keep the checklist's storage key and JSON shape.

The browser code accesses Jira issue entity property todos through the Jira REST API. Migration tests must compare values per issue before and after the Forge installation; assuming empty UI means no stored checklist would risk data loss.

03 · JWT and tenant isolation

Recheck every permission boundary.

The original Express /todolist route uses Connect authentication and the descriptor requests READ and WRITE. A Forge resolver needs separately reviewed scopes, app-versus-user access and negative tests for unauthorized issue reads/edits. Do not copy JWT assumptions into Forge.

04 · HTML rendering security

Never carry untrusted markup directly into the UI.

The old browser script inserts checklist text as HTML rather than text. That is an injection risk worth removing in a rewrite. Render escaped text and validate storage input instead of preserving an unsafe presentation behavior.

05 · Error and empty states

Don't make API failure look like deleted data.

On a failed issue-property request, the sample UI clears the checklist view. A Forge version should explicitly distinguish first-use empty state, transient error and missing permission, and must not persist a blank list after a fetch failure.

06 · Real environment/rollback

Validate the installed app, not a template.

The descriptor uses a development placeholder for its backend URL and has an install event. A proper cutover requires an owner-controlled Forge app ID, staged installation, migration data checks, documented tenant scope, rollback conditions and explicit deployment approval.

Example acceptance conditions, not completed tests

DATA: For N permitted issues with a prior 'todos' entity property, post-migration values match the agreed key and JSON structure.
AUTH: An authorized editor can update a checklist; an unauthorized user cannot read or modify a restricted issue.
UX: Previously visible checklist functionality remains discoverable in the new issue view; API errors never appear as an empty checklist.
ROLLBACK: Owner identifies a recoverable pre-cutover state, required backups and a go/no-go decision before activating production.

Where the technical review ends

This review can propose a bounded migration plan; it cannot prove that the target app will work until the client's environment, actual source behaviour and applicable Forge modules are tested. Customer-owned deployments and business data require separate authorization and a written scope.
